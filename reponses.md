# TP1 — SOAP et WSDL · Réponses

Environnement : JDK 17 (Temurin 17.0.16), Maven 3.9.15, Metro `jaxws-rt` 4.0.2, `curl.exe` sous PowerShell.
Service : `http://localhost:8080/bib/EmpruntService` (WSDL : `?wsdl`).

## Étape 1 — Créer et lancer le service

`mvn compile exec:java` affiche `WSDL : http://localhost:8080/bib/EmpruntService?wsdl`, et l'URL répond HTTP 200 avec le WSDL généré (commentaire « Generated by XML-WS Runtime 4.0.2 »).

### Q1. Quelle annotation fait de `EmpruntService` un service web ? Et de `LivreIndisponibleException` une erreur déclarée dans le contrat ?

- **`@WebService`** (`jakarta.jws.WebService`) sur la classe `EmpruntService` en fait un service web : JAX-WS expose ses méthodes publiques comme opérations. Ses attributs donnent les noms du contrat : `serviceName = "EmpruntService"` → `<service>`, `portName = "EmpruntPort"` → `<port>`, `targetNamespace = "http://supnum.mr/bib"` → namespace du WSDL. `@WebMethod`, `@WebParam` et `@WebResult` précisent les opérations, les noms des paramètres (`idAdherent`, `isbn`, `numeroEmprunt`) et des résultats (`emprunt`, `penalite`).
- **`@WebFault`** (`jakarta.xml.ws.WebFault`) sur `LivreIndisponibleException` en fait une **Fault déclarée** : comme la méthode `emprunterLivre` la déclare dans son `throws`, JAX-WS ajoute au WSDL un `<message name="LivreIndisponibleException">`, un `<fault>` dans le `portType` et le `binding`, et l'élément XSD `LivreIndisponible` (nom tiré de `name = "LivreIndisponible"`), dont le contenu est le `faultInfo` renvoyé par `getFaultInfo()`.

### Q2. Pourquoi les classes de données doivent-elles avoir un constructeur vide ?

Parce que la conversion XML ↔ Java est faite par **JAXB**, qui travaille par réflexion. Pour **désérialiser** un message (XML → objet), JAXB doit d'abord créer une instance **sans connaître d'arguments** (`new Emprunt()`), puis remplir les champs un par un à partir des éléments XML (`numero`, `dateRetour`…). Il ne sait pas quel constructeur avec paramètres appeler, ni dans quel ordre. Sans constructeur sans argument, JAX-WS refuse de générer le contrat ou de traiter les messages (`IllegalAnnotationsException` : « does not have a no-arg default constructor »). Cela concerne `Emprunt` et `LivreIndisponibleInfo`, mais aussi les classes *wrapper* que JAX-WS génère pour chaque opération.

## Étape 2 — Lire le WSDL généré

Le WSDL se lit de bas en haut :

| Élément | Contenu dans le WSDL généré |
|---|---|
| `service` | `EmpruntService`, port `EmpruntPort`, `soap:address location="http://localhost:8080/bib/EmpruntService"` |
| `binding` | `EmpruntPortBinding` (type `tns:EmpruntService`) : `soap:binding style="document"`, `transport=".../soap/http"`, `soap:body use="literal"`, `soapAction=""` |
| `portType` | `EmpruntService` : opérations `rendreLivre` et `emprunterLivre` (cette dernière avec le `fault` `LivreIndisponibleException`) |
| `message` | `emprunterLivre`, `emprunterLivreResponse`, `rendreLivre`, `rendreLivreResponse`, `LivreIndisponibleException` (une `part` chacun) |
| `types` | aucun type écrit en ligne : un `xsd:import` vers `schemaLocation="http://localhost:8080/bib/EmpruntService?xsd=1"` |

### Q1. URL du service, opérations, messages d'entrée et de sortie

**URL** (dans `service/port/soap:address`) : `http://localhost:8080/bib/EmpruntService`

| Opération | Message d'entrée | Message de sortie | Fault |
|---|---|---|---|
| `emprunterLivre` | `tns:emprunterLivre` → élément `emprunterLivre` (`idAdherent`, `isbn`) | `tns:emprunterLivreResponse` → élément `emprunterLivreResponse` (`emprunt` : `numero`, `dateRetour`) | `tns:LivreIndisponibleException` → élément `LivreIndisponible` |
| `rendreLivre` | `tns:rendreLivre` → élément `rendreLivre` (`numeroEmprunt`) | `tns:rendreLivreResponse` → élément `rendreLivreResponse` (`penalite`) | aucune |

Chaque message contient une seule `part name="parameters"` qui référence un **élément** du schéma : c'est le style *document/literal wrapped*, où l'élément porte le nom de l'opération.

### Q2. Style, use, version SOAP

- **Style : `document`** (`<soap:binding style="document">`).
- **Use : `literal`** (`<soap:body use="literal"/>` pour chaque entrée et sortie, `<soap:fault use="literal"/>`).
- **SOAP 1.1** : le binding utilise le namespace `xmlns:soap="http://schemas.xmlsoap.org/wsdl/soap/"` (extension WSDL pour SOAP 1.1 ; SOAP 1.2 utiliserait `http://schemas.xmlsoap.org/wsdl/soap12/`) et le transport `http://schemas.xmlsoap.org/soap/http`. C'est le comportement par défaut de JAX-WS sans `@BindingType`. L'étape 3 l'a confirmé : un message SOAP 1.2 est rejeté avec `VersionMismatch`.

### Q3. Types XSD générés pour `isbn` et `dateRetour` ; la règle de l'ISBN apparaît-elle ?

Dans le schéma `?xsd=1` :

```xml
<xs:element name="isbn" type="xs:string" minOccurs="0"/>
<xs:element name="dateRetour" type="xs:string" minOccurs="0"/>
```

- `isbn` → **`xs:string`** (le type Java est `String`).
- `dateRetour` → **`xs:string`** aussi, et non `xs:date`, car le champ Java est un `String`. Le contrat ne dit pas que c'est une date.
- **La règle de format de l'ISBN n'apparaît pas.** Le `Pattern` `97[89]-\d-\d{2,5}-\d{2,6}-\d` est dans le **code Java**, invisible pour JAX-WS. Aucun `xs:pattern` n'est généré : un client qui lit le contrat ne peut pas connaître la règle, il ne la découvre qu'en recevant une Fault (étape 4). Tous les éléments sont en plus `minOccurs="0"` (optionnels), car un `String` Java peut être `null`. Le contrat généré est donc **plus faible** que le comportement réel du service. C'est une limite du code-first, que la partie B corrige (`IsbnType` avec `xs:pattern`, `xs:date`).

### Q4. Dans la requête SoapUI, `idAdherent` et `isbn` portent-ils un préfixe d'espace de noms ?

**Non.** SoapUI génère :

```xml
<soapenv:Envelope xmlns:soapenv="http://schemas.xmlsoap.org/soap/envelope/" xmlns:bib="http://supnum.mr/bib">
   <soapenv:Header/>
   <soapenv:Body>
      <bib:emprunterLivre>
         <idAdherent>A-117</idAdherent>
         <isbn>978-1-234-5678-9</isbn>
      </bib:emprunterLivre>
   </soapenv:Body>
</soapenv:Envelope>
```

Seul l'élément racine `bib:emprunterLivre` est qualifié (c'est un élément **global** du schéma, donc dans le namespace `http://supnum.mr/bib`). Les paramètres sont des éléments **locaux**, et le schéma généré n'a **pas d'attribut `elementFormDefault`**, qui vaut donc `unqualified` par défaut : les éléments locaux n'appartiennent à aucun namespace et s'écrivent sans préfixe. Écrire `<bib:isbn>` serait une erreur : JAXB ne reconnaîtrait pas l'élément et le paramètre vaudrait `null` (observé à l'étape 3 avec `<bib:numero>`). Réponse obtenue : `E-2026-0812`.

### Q5. Dans l'onglet Raw : où voit-on HTTP, XML, SOAP ? Rôle de chaque standard et du WSDL

Dans l'onglet *Raw* de la requête, on voit :

```
POST http://localhost:8080/bib/EmpruntService HTTP/1.1      ← HTTP : ligne de requête
Content-Type: text/xml;charset=UTF-8                          ← HTTP : en-têtes
SOAPAction: ""                                                ← HTTP (en-tête propre à SOAP 1.1)
Content-Length: ...
Host: localhost:8080

<soapenv:Envelope ...>                                        ← XML : tout le corps
   <soapenv:Header/>                                          ← SOAP : Envelope / Header / Body
   <soapenv:Body> <bib:emprunterLivre>...</bib:emprunterLivre> </soapenv:Body>
</soapenv:Envelope>
```

| Standard | Où on le voit | Rôle |
|---|---|---|
| **HTTP** | Ligne `POST … HTTP/1.1` et en-têtes (`Content-Type`, `SOAPAction`, `Host`) | **Transport** : acheminer le message jusqu'à l'URL du service et ramener la réponse (avec un code de statut : 200, ou 500 pour une Fault). |
| **XML** | Le corps de la requête (balises, namespaces `xmlns:`) | **Format de données** : syntaxe commune, indépendante du langage, que Java, .NET, PHP… savent lire. Les namespaces évitent les conflits de noms. |
| **SOAP** | La structure `Envelope` / `Header` / `Body` (namespace `http://schemas.xmlsoap.org/soap/envelope/`) | **Protocole de messagerie** : enveloppe standard qui sépare les métadonnées (Header : jeton, sécurité…) du contenu métier (Body) et définit un format d'erreur standard (Fault). |
| **WSDL** | Il n'est **pas** dans le message : il est lu **avant**, par SoapUI, pour construire cette requête | **Contrat** : décrit quelles opérations existent (`portType`), quelles données circulent (`types`/`message`), comment les emballer (`binding` : SOAP 1.1, document/literal) et où envoyer (`service`). C'est grâce à lui que SoapUI a pu générer la requête automatiquement. |

## Étape 3 — Envoyer des messages SOAP

Commande utilisée (PowerShell, depuis `C:\TP_SOA`) :

```powershell
curl.exe -i -X POST http://localhost:8080/bib/EmpruntService -H "Content-Type: text/xml; charset=utf-8" -H 'SOAPAction: \"\"' --data-binary "@xml/01-emprunter.xml"
```

Résultats observés :

| Fichier | HTTP | Réponse |
|---|---|---|
| `01-emprunter.xml` (SOAP 1.1) | 200 OK | `emprunterLivreResponse` → `numero = E-2026-0813`, `dateRetour = 2026-12-08` |
| `02-emprunter-12.xml` (SOAP 1.2) | 500 | Fault `S:VersionMismatch` |
| `03-erreurs.xml` (5 erreurs) | 500 | Fault `S:Client` : balise attendue `Envelope`, obtenue `envelope` |
| `03-erreurs-corrige.xml` | 200 OK | `rendreLivreResponse` → `penalite = 0` |

### Q1. Pourquoi la requête utilise-t-elle POST, même pour lire une information ?

Parce que SOAP n'utilise HTTP que comme **transport** : tout le sens de l'appel (opération, paramètres, en-têtes) est dans l'enveloppe XML, qui doit voyager dans le **corps** de la requête. Une requête GET n'a pas de corps. Le binding SOAP 1.1/HTTP du WSDL (`transport="http://schemas.xmlsoap.org/soap/http"`) impose donc POST vers une URL unique, quelle que soit l'opération. La sémantique HTTP (GET = lecture, POST = écriture) n'est pas utilisée : c'est l'élément du Body (`emprunterLivre`, `rendreLivre`) qui dit quoi faire. Le seul GET du service est la récupération du contrat (`?wsdl`, `?xsd=1`).

### Q2. Le bloc `jeton` du Header a-t-il empêché le traitement ? Pourquoi ?

Non : `01-emprunter.xml` a reçu **HTTP 200** avec un numéro d'emprunt. Le service ne déclare aucun en-tête dans son WSDL et aucun handler ne traite `bib:jeton`. Or, selon SOAP, un bloc de Header **sans `mustUnderstand="1"`** est facultatif : le destinataire qui ne le comprend pas a le droit de l'ignorer. Metro l'a donc simplement ignoré (voir l'étape 4, Q4, pour le cas contraire).

### Q3. Que répond le service au message SOAP 1.2 ? Explication avec le binding

```
HTTP/1.1 500 Internal Server Error
<S:Envelope xmlns:S="http://schemas.xmlsoap.org/soap/envelope/">…
  <faultcode>S:VersionMismatch</faultcode>
  <faultstring>Impossible de créer le message SOAP. Attente de Envelope dans l'espace de noms
  http://schemas.xmlsoap.org/soap/envelope/, mais http://www.w3.org/2003/05/soap-envelope obtenu</faultstring>
```

Le binding lu à l'étape 2 est un binding **SOAP 1.1** (namespace `http://schemas.xmlsoap.org/wsdl/soap/`, transport `.../soap/http`). L'endpoint n'accepte donc que des enveloppes dans le namespace `http://schemas.xmlsoap.org/soap/envelope/`. La version SOAP est identifiée **uniquement par le namespace de l'enveloppe**. En recevant le namespace 1.2, le serveur répond par la Fault standard `VersionMismatch`, rédigée elle-même en SOAP 1.1 (sa seule version connue).

### Q4. Les cinq erreurs du dernier message et leur correction

| # | Erreur | Correction |
|---|---|---|
| 1 | `<soap:envelope>` en minuscule (XML est sensible à la casse) | `<soap:Envelope>` |
| 2 | `xmlns:bib="http://supnum.mr/bibliotheque"` : mauvais namespace cible | `xmlns:bib="http://supnum.mr/bib"` |
| 3 | `<bib:numero>` : le paramètre s'appelle `numeroEmprunt`, et il est non qualifié (sans préfixe) | `<numeroEmprunt>E-2026-0812</numeroEmprunt>` |
| 4 | `</rendreLivre>` ne ferme pas `<bib:rendreLivre>` (XML mal formé) | `</bib:rendreLivre>` |
| 5 | `soap:Header` placé **après** `soap:Body` (la norme impose Header puis Body) | Déplacer le Header avant le Body |

Version corrigée : `xml/03-erreurs-corrige.xml` → HTTP 200, `penalite = 0`.

En corrigeant **une erreur à la fois**, voici ce que le serveur a renvoyé :

| Erreurs restantes | Réponse du serveur |
|---|---|
| 1, 2, 3, 4, 5 | 500, `Client` : `envelope` au lieu de `Envelope` |
| 2, 3, 4, 5 | 500, `Client` : « Méthode de répartition introuvable pour {http://supnum.mr/bibliotheque}rendreLivre » |
| 2, 3, 5 | même Fault (namespace) |
| 3, 5 | **200 OK**, `penalite = 0` |
| 3 seule | **200 OK**, `penalite = 0` |
| 5 seule | **200 OK**, `penalite = 0` |
| 4 seule | 500, `Server` : `jakarta.xml.bind.UnmarshalException` |

**Erreurs qui ne déclenchent aucune erreur côté serveur :**

- **Erreur 5 (Header après Body)** : Metro est permissif. Il trouve le Body, traite l'opération et ignore le Header mal placé (qui, de toute façon, n'est pas obligatoire). Le message n'est pourtant pas conforme à SOAP 1.1.
- **Erreur 3 (`bib:numero`)** : le style *document/literal wrapped* fait que JAXB **ignore les éléments inconnus**. `numeroEmprunt` est simplement absent, donc il vaut `null`. Avant l'étape 4, `rendreLivre` renvoyait `0` sans rien vérifier : la requête « réussit » avec un résultat faux. C'est l'erreur la plus dangereuse. *Après l'ajout de la vérification de l'étape 4, la même requête renvoie bien une Fault `Client` : « Numéro d'emprunt inconnu : null ».*
- **Erreur 4 (balise fermante)** : elle déclenche une erreur quand elle est seule, mais elle est **masquée** dans le message complet. Le parseur StAX lit le XML **en flux** : il échoue sur la première erreur rencontrée (le nom de l'enveloppe, puis le namespace) avant d'atteindre la balise fermante. On remarque aussi que, seule, elle produit un faultcode `Server` alors que la faute vient du client.

## Étape 4 — Provoquer et construire des Faults

Fichiers envoyés (variantes de `01-emprunter.xml`) :

| Fichier | Cas | HTTP | faultcode | faultstring |
|---|---|---|---|---|
| `04-isbn-invalide.xml` | ISBN `978-2-10` | 500 | `S:Client` | `ISBN mal formé : 978-2-10` |
| `05-livre-indisponible.xml` | ISBN `978-2-10-074444-4` | 500 | `S:Server` | `Livre indisponible` |
| `06-mustunderstand-1.xml` | `jeton` avec `mustUnderstand="1"` | 500 | `S:MustUnderstand` | `MustUnderstand headers:[{http://supnum.mr/bib}jeton] are not understood` |
| `07-mustunderstand-0.xml` | `jeton` avec `mustUnderstand="0"` | 200 | — | emprunt `E-2026-0814` créé |
| `08-rendre-invalide.xml` | `rendreLivre` avec `X-1999-0001` | 500 | `S:Client` | `Numéro d'emprunt inconnu : X-1999-0001` |

### Q1. Cas 1 et 2 : faultcode, faultstring, code HTTP

- **Cas 1 (ISBN mal formé)** : `faultcode = S:Client`, `faultstring = ISBN mal formé : 978-2-10`, **HTTP 500**.
- **Cas 2 (livre déjà emprunté)** : `faultcode = S:Server`, `faultstring = Livre indisponible`, **HTTP 500**.

En SOAP 1.1 sur HTTP, toute Fault est renvoyée avec le code **500 Internal Server Error**, même quand la faute vient du client. C'est le faultcode, et non le code HTTP, qui dit qui est en faute.

### Q2. Contenu de `<detail>` (cas 2) et sa description dans le WSDL

```xml
<detail>
  <ns2:LivreIndisponible xmlns:ns2="http://supnum.mr/bib">
    <isbn>978-2-10-074444-4</isbn>
    <retourPrevu>2026-12-02</retourPrevu>
  </ns2:LivreIndisponible>
</detail>
```

C'est l'objet `LivreIndisponibleInfo` (le `faultInfo` de l'exception) sérialisé par JAXB. Sa structure est décrite dans le contrat à plusieurs endroits :

- **XSD** (`?xsd=1`) : `<xs:element name="LivreIndisponible" type="tns:livreIndisponibleInfo"/>` et le `complexType livreIndisponibleInfo` (`isbn`, `retourPrevu`). Le nom de l'élément vient de `@WebFault(name = "LivreIndisponible")`.
- **`message`** : `<message name="LivreIndisponibleException"><part name="fault" element="tns:LivreIndisponible"/></message>`.
- **`portType`** : `<fault message="tns:LivreIndisponibleException" name="LivreIndisponibleException"/>` dans l'opération `emprunterLivre`.
- **`binding`** : `<fault name="LivreIndisponibleException"><soap:fault … use="literal"/></fault>`.

Le cas 1, lui, n'a **pas de `<detail>`** : c'est une Fault construite à la main (`SOAPFaultException`), non déclarée dans le contrat.

### Q3. Code choisi par JAX-WS pour le livre indisponible : client ou serveur ? Qu'aurions-nous choisi ?

JAX-WS a choisi **`Server`**. Pour une exception métier déclarée (`@WebFault`), JAX-WS utilise toujours le faultcode `Server` par défaut, sans regarder la sémantique de l'erreur.

Pourtant, ce n'est **pas une panne du serveur** : le serveur fonctionne normalement et applique une règle métier. Ce n'est pas non plus vraiment une requête malformée. Selon la spécification SOAP, `Client` signifie « le message est incorrect ou ne contient pas les informations nécessaires, **ne le renvoyez pas tel quel** », et `Server` signifie « le problème vient du traitement, **le même message pourrait réussir plus tard** ». Un livre indisponible pourra être emprunté après le 2026-12-02 : `Server` est donc défendable.

**Notre choix : `Client`** (`Sender` en 1.2). Renvoyer immédiatement la même demande échouera de la même façon, c'est la demande du client qui ne peut pas être satisfaite, et `Server` laisse penser à tort à un incident technique (risque de relances automatiques, alertes de supervision). L'important est surtout la **Fault typée avec `detail`**, qui permet au client de réagir proprement (afficher la date `retourPrevu`).

### Q4. `mustUnderstand="1"` puis `"0"`

- **`mustUnderstand="1"`** : le serveur refuse **tout le message** avec une Fault `S:MustUnderstand` (« headers:[{http://supnum.mr/bib}jeton] are not understood »), HTTP 500. L'opération n'est **pas exécutée** : le livre `978-2-07-036823-5` n'a pas été emprunté. La règle SOAP est qu'un destinataire qui ne sait pas traiter un bloc obligatoire **ne doit pas traiter le message**.
- **`mustUnderstand="0"`** (ou attribut absent) : le bloc est facultatif, il est ignoré. Le même ISBN est bien emprunté (HTTP 200, `E-2026-0814`). Cela confirme qu'avec `"1"` rien n'avait été traité.

### Q5. Différences entre notre Fault 1.2 (`03-fault-sender-12.xml`) et les Faults 1.1 reçues

Validée avec un parseur XML (Python `xml.dom.minidom`, équivalent de `xmllint --noout`) : **XML bien formé**, racine `soap:Envelope` dans `http://www.w3.org/2003/05/soap-envelope`.

| | SOAP 1.1 (reçue) | SOAP 1.2 (écrite) |
|---|---|---|
| Namespace de l'enveloppe | `http://schemas.xmlsoap.org/soap/envelope/` | `http://www.w3.org/2003/05/soap-envelope` |
| Code | `<faultcode>S:Client</faultcode>` (texte simple) | `<soap:Code><soap:Value>soap:Sender</soap:Value></soap:Code>` (structuré, sous-codes possibles avec `soap:Subcode`) |
| Noms des codes | `Client` / `Server` | `Sender` / `Receiver` |
| Message | `<faultstring>` (un seul texte) | `<soap:Reason><soap:Text xml:lang="fr">` (plusieurs langues possibles) |
| Détail | `<detail>` (sans préfixe, non qualifié) | `<soap:Detail>` (qualifié dans le namespace SOAP 1.2) |
| Éléments enfants | non qualifiés (`faultcode`, `faultstring`) | tous qualifiés (`soap:Code`, `soap:Reason`…) |
| Code HTTP associé | toujours 500 | 400 pour `Sender`, 500 pour `Receiver` |
| Content-Type | `text/xml` | `application/soap+xml` |
